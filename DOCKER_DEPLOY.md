# DataMind — Docker Compose deployment

Runs the whole stack as 8 containers: **nginx (frontend)** + **backend** + the **six agents**
(Heimdall, ARIA, SAGE, VALKYRIE, RAVEN, SPYDER). PostgreSQL stays external (your Supabase DB).

Only **port 80** is exposed to the host. Backend (8000) and agents (8001–8006) talk to each
other on a private Docker network by service name — they are never exposed publicly.

---

## 1. Where these files go in the repo

Copy the contents of this `datamind-docker/` folder into the **root of the DataMind repo**, so you end up with:

```
DataMind/
├── docker-compose.yml            ← new
├── .dockerignore                 ← new
├── docker/                       ← new
│   ├── Dockerfile.backend
│   ├── Dockerfile.agents
│   ├── Dockerfile.frontend
│   ├── nginx.conf
│   ├── requirements.agents.txt
│   ├── entrypoint-backend.sh
│   ├── entrypoint-aria.sh
│   └── entrypoint-sage.sh
├── backend/
│   └── app/agents/http_clients.py   ← REPLACE existing file with the patched one
├── Agents/ ...
└── frontend/ ...
```

> The **only source-code change** is `backend/app/agents/http_clients.py`. The patched version
> reads agent URLs from environment variables (defaulting to `localhost` so your existing
> non-Docker workflow still works unchanged). Everything else is additive.

---

## 2. The one required code change — why

Today the backend reaches each agent at `http://localhost:800X`. Inside containers `localhost`
means "this container", so those calls would fail. The patched `http_clients.py` reads:

```
HEIMDALL_URL  ARIA_URL  SAGE_URL  VALKYRIE_URL  SPYDER_URL  RAVEN_URL
```

`docker-compose.yml` sets these to the service names (`http://heimdall:8001`, etc.). When the
env vars are absent (your laptop, `start_all.py`), it falls back to `localhost` — no behaviour change.

---

## 3. Configure `backend/.env`

Compose feeds your existing `backend/.env` into every service (`env_file`). Make sure it has the
usual values — `DATABASE_URL`, `SECRET_KEY`, `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL`,
`DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD/DB_SSLMODE`, `TARGET_SCHEMA`, etc.

Two notes:
- `DATABASE_URL` / `DB_HOST` must point at a DB reachable **from inside the container** — for
  Supabase that's a public host, so it works as-is.
- For the **first boot only**, add `SEED_DB=true` to create the admin user + agent configs, then
  remove it (or set back to `false`) so it doesn't re-run.

## 4. Build and start

From the repo root on your EC2 box:

```bash
docker compose build          # builds 3 images (agents image is the heavy one — torch + models)
docker compose up -d
docker compose ps             # watch until all are healthy
docker compose logs -f backend
```

First build is slow (downloads torch + Python deps). First request is also slow because Heimdall
and RAVEN download embedding models into the `hf_models` volume — subsequent restarts are fast.

Open `http://<your-ec2-public-dns>/` → log in with `admin@slm.local / Admin@1234`.

## 5. EC2 Security Group

With Compose, you only need:

| Port | Source | Why |
|------|--------|-----|
| 80   | 0.0.0.0/0 | the app (nginx) |
| 443  | 0.0.0.0/0 | when you add TLS |
| 22   | **My IP** | SSH |

**Remove 5173 and 8000** — they're no longer exposed. Agents 8001–8006 were never exposed.

## 6. Startup order (handled automatically)

```
ARIA  ──(bootstrap schema_reference.json → shared volume)──┐
                                                           ▼
Heimdall, VALKYRIE, RAVEN, SPYDER start ······· SAGE (waits for shared schema)
                                                           │
                          all six agents healthy ──────────┤
                                                           ▼
                                                       backend (alembic migrate → uvicorn)
                                                           │ healthy
                                                           ▼
                                                       frontend / nginx  :80
```

`schema_reference.json` is generated by ARIA at startup and published to a shared volume that SAGE
reads (`SCHEMA_FILE_PATH=/shared/schema_reference.json`). After changing domains/tables, regenerate it:

```bash
docker compose exec aria python bootstrap_schema.py && \
docker compose exec aria cp schema_reference.json /shared/schema_reference.json && \
docker compose exec aria curl -s -X POST http://localhost:8002/schema/reload && \
docker compose exec sage curl -s -X POST http://localhost:8003/schema/reload
```

## 7. Add HTTPS (recommended)

Easiest is a small companion (Caddy or nginx + certbot) terminating TLS on 443 and forwarding to
the `frontend` container, or run certbot on the host. Requires a real domain pointing at the instance.

## 8. Common issues

- **Agent unhealthy / backend won't start** — `docker compose logs <service>`. Usually a missing
  `.env` value (LLM key, DATABASE_URL) or the DB not reachable from the container.
- **SAGE can't resolve tables** — the shared schema wasn't generated. Check `docker compose logs aria`
  for the bootstrap step and confirm `/shared/schema_reference.json` exists
  (`docker compose exec sage ls -l /shared`).
- **`alembic upgrade` fails** — DATABASE_URL wrong, or the DB user lacks rights. The app may still
  start; fix the URL and `docker compose restart backend`.
- **Slow first response** — embedding models downloading. One-time per `hf_models` volume.

---

## 9. About Kubernetes

The **Dockerfiles** here are fully reusable on Kubernetes — the images are the portable part.
The `docker-compose.yml` itself does not run on K8s; you'd rewrite it as Deployments + Services +
an Ingress (replacing nginx) + ConfigMap/Secret (replacing `env_file`) + a PersistentVolumeClaim
for the shared `schema_data`. Because the inter-agent URLs are now env-driven, that port maps
cleanly to K8s Service DNS with no further code changes.
